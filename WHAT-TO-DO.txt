Taiyabah Masjid — the admin signpost, and two-step verification that is real
============================================================================

Copy these into the repo at the same paths, overwriting what is there, then
commit and push. `portals/` is a new folder.

  portals/index.html            <- NEW. The hub an administrator lands on
  portals/app.js                <- NEW
  portals/config.js             <- NEW. Same values as account/config.js
  account/index.html            <- adds the (hidden) admin button
  account/app.js                <- reveals it only to administrators
  db/011_require_two_step.sql   <- NOT applied yet. Read step 2 below first
  db/_test_two_step.sql         <- LOCAL ONLY. Never run against Supabase
  db/_test_stubs.sql            <- LOCAL ONLY
  db/_test_supabase_stub.sql    <- LOCAL ONLY. Belongs in the madrasah-db repo
  README.md
  DEPLOY.md

`portals/config.js` holds the same publishable key the other portals hold. That
key is designed to be public; row level security is what protects the data. The
secret key must never appear in any of these files.

1. The signpost
---------------
An administrator signs in at /account/ as usual and gets a second button, "Go to
the admin area", leading to /portals/. That page lists the staff areas their
account can open — today the venue portal and the madrasah portal.

It is a signpost and nothing else. It holds no data: no booking, no application,
no child's record. If someone got past every check on it they would see two
links. Each portal still asks for the authenticator code when it is opened.

It fails closed. The role is read from user_roles under RLS, and if that read
errors for any reason the button stays hidden. A button that appears when we
cannot confirm the role would be worse than none, because it tells an attacker
which login is worth pursuing.

Administrators only, for now. Hall office staff and teachers still use their own
links. Widening it later is one line in portals/app.js.

2. The part that actually matters — apply 011
---------------------------------------------
Until this migration is applied, the authenticator code on the staff portals is
checked IN JAVASCRIPT ONLY. Anyone holding a staff email address and password
can skip the page entirely — curl, Postman, the browser console — and read hall
bookings, nikah requests and admission applications straight from the API. The
code prompt is a locked front door on a building with the windows open.

Before you apply it: every member of staff must have set up their authenticator.
The migration checks this itself and REFUSES to apply while anyone holding
admin, hall_office or teacher has no verified factor — it prints their email
addresses. Get those people to sign in to their portal once; it walks them
through the setup. Do not work around that check. An administrator who is locked
out is an administrator who cannot grant roles to let themselves back in.

Then: run db/011_require_two_step.sql in the Supabase SQL editor, sign in to the
venue portal, and confirm a booking still opens and saves.

What it does not solve: two-step stops a stolen password. It does nothing about
a borrowed, unlocked laptop — a session already verified stays trusted until it
expires. The office still needs to lock its screens.

The bottom of 011 carries the exact SQL to put everything back if it goes wrong.
Reverting reopens the hole, so treat it as buying an hour rather than a fix.

3. Tested
---------
  24 SQL assertions in _test_two_step.sql, run against a database built from
  every migration in order, all as a role that is genuinely subject to RLS.
  Staff read nothing before the code and everything after it; an administrator
  can still see their own role beforehand, which is what makes the button work;
  the public can still submit; and a scan of pg_policies fails the build if any
  future policy skips the check.

  A browser test drives both pages: a customer gets no button, an administrator
  does, hall office staff do not, a failed role lookup shows nothing, and the
  hub reads no data tables at all.
